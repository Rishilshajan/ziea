1 Before you start

Gather these so you're not hunting mid-deploy.

  • Access to the GitHub account that owns Rishilshajan/ziea.
  • Your Supabase project URL, anon key, and service-role key (from Supabase → Project Settings → API). These live in your local .env.local today.
  • hPanel login for the plan hosting ziea.in.
  • Access to Google Cloud Console (for the OAuth redirect update) and the Supabase Auth settings.
⚠️
Never commit secrets. Confirm .env.local is listed in .gitignore. Your keys go into Hostinger's Environment Variables screen (Step 4), not into the repo.

2 Push the code to GitHub

Hostinger deploys whatever is on your GitHub branch, so make sure your latest work is pushed.

# from the project folder
git status                 # confirm a clean tree / see what's unstaged
git add -A
git commit -m "Prepare for Hostinger deploy"
git push origin master
💡
No code changes are required for Hostinger. The package.json already has the scripts it expects — build: "next build" and start: "next start" — and next.config.ts already whitelists ziea.in for images.

3 Create the app in hPanel

This connects your GitHub repo to Hostinger and sets up the Node app.

  1. Log into hPanel → click Websites in the left sidebar.
  2. Click Add Website → choose Deploy Web App.
  3. Pick Import Git Repository → click Authorize and grant Hostinger access to your GitHub account.
  4. Select the repository Rishilshajan/ziea and the branch master.
  5. Hostinger auto-detects Next.js. Confirm: Node version 22.x (or 20.x), build command npm run build, start command npm run start.
  6. Attach the domain ziea.in (it's this plan's domain, so it should be offered automatically).
  7. Do not click Deploy yet — first add the environment variables (Step 4). If the UI deploys immediately, that's fine; you'll add the vars and redeploy.
🔑
One GitHub account per plan. Hostinger links a single GitHub account to this hosting plan — authorize the account that owns the ZIEA repo.

4 Environment variables

In the app's Environment Variables screen, add these exact keys. The first three are your existing secrets; the last three switch the site to the ziea.in origin and turn on the same-origin image CDN.

KeyValueNotes
NEXT_PUBLIC_SUPABASE_URLyour Supabase URLfrom .env.local
NEXT_PUBLIC_SUPABASE_ANON_KEYyour anon keyfrom .env.local
SUPABASE_SERVICE_ROLE_KEYyour service-role keysecret — server only
NEXT_PUBLIC_SITE_URLhttps://ziea.infixes canonicals / OG / sitemap
NEXT_PUBLIC_ASSET_BASE_URLhttps://ziea.in/cdnpublic URL prefix for images
ASSET_UPLOAD_DIR/home/u328706839/domains/ziea.in/public_html/cdnwhere uploads are written
⚠️
Verify the upload path. u328706839 is inferred from your FTP username. Open hPanel → Files → File Manager, navigate to public_html, and confirm the absolute path shown. Adjust ASSET_UPLOAD_DIR to match <that path>/cdn. You don't need to create the cdn folder — the upload route creates it automatically on first use.
✅
You can safely omit the old BUNNY_* keys — they're legacy from a previous CDN and are no longer used by the code.

5 Deploy

Now trigger the build.

  1. Click Deploy (or Redeploy if the app was created already).
  2. Watch the build log. You'll see npm install, then next build compiling routes, then the server starting.
  3. When it finishes, Hostinger shows the deployment as successful with a timestamp. SSL for ziea.in is issued automatically.
💡
Behind the scenes Hostinger stores the built app under /home/<user>/domains/ziea.in/nodejs and serves static files from public_html, wiring routing with an auto-generated .htaccess. You don't manage any of that by hand.

6 Image CDN setup

This is the bonus you get by running on Hostinger: images are written to and served from the same origin, removing the slow Vercel-optimizer → Supabase hop.

PieceWhat happens
Admin uploads an image/api/upload writes the file to ASSET_UPLOAD_DIR (public_html/cdn/...)
File gets a URLReturned as https://ziea.in/cdn/<folder>/<file>
Shopper loads itServed same-origin from ziea.in — no optimizer hop → faster LCP
🔑
Old images keep working. Anything uploaded while on Vercel still points at Supabase Storage and continues to load (the supabase.co host stays whitelisted in next.config). Only new uploads use the Hostinger CDN. Migrate old files later only if you want everything on one origin.

7 Supabase & Google config

Two external dashboards need to learn the new ziea.in origin, or login (especially Google) will break with redirect errors. Do these once, after the first successful deploy.

Supabase → Authentication → URL Configuration

  • Set Site URL to https://ziea.in.
  • Add https://ziea.in/auth/callback to Redirect URLs (keep the Vercel one too during transition).

Google Cloud Console → APIs & Services → Credentials → your OAuth client

  • Add https://ziea.in to Authorized JavaScript origins.
  • Ensure the Supabase callback (https://<project>.supabase.co/auth/v1/callback) is in Authorized redirect URIs.
⚠️
This is the fix for the earlier "Google login redirects to localhost / connection refused" issue — it was always a dashboard config matter, not a code bug.

8 Verify it's live

Walk this checklist after deploy to confirm every subsystem works on the new origin.

  • https://ziea.in loads the home page over HTTPS (padlock shown).
  • Collections list + a product page open and show real products.
  • Sign up / log in with email works; Google sign-in completes without a redirect error.
  • Add to cart / wishlist persists after refresh (server actions working).
  • Buy Now opens WhatsApp and the order appears in /admin/orders.
  • Admin login reaches /admin; upload a test image in Products/Branding → its URL is https://ziea.in/cdn/... and it renders.
  • https://ziea.in/sitemap.xml and /robots.txt resolve with the ziea.in origin.

9 Redeploys (CI/CD)

After the first setup, shipping changes is just a Git push.

# make changes, then
git add -A
git commit -m "Your change"
git push origin master     # Hostinger auto-builds & redeploys
🔑
Every push to master goes live. For safety, do risky work on a branch and only merge to master when you're ready to ship. You can also trigger a manual Redeploy from the app dashboard, and use the Restart button if the Node process ever needs a kick.
